# 广告快跳（AdAuto）

一个 Android 悬浮球助手：**常驻屏幕左上角的球形助手 + 无障碍自动跳过广告**。

- 应用以**悬浮球**形态常驻在屏幕左上角，可随意拖动。
- 通过**无障碍服务（Accessibility）**读取界面内容，无需 Root。
- 检测到界面进入广告状态（例如出现 **"上滑继续观看短剧"**、"跳过广告"、"关闭广告" 等），自动执行对应操作跳过广告。

> 🎯 **当前为「红果免费短剧」App（`com.phoenix.read`）专用适配**：内置规则、正剧播放保护、
> 穿山甲（Pangle）视频广告识别、窗口切换延迟重扫等均针对红果的广告形态做了专门调优，兼容性最稳。
>
> **默认只在“规则设置 → 自动跳过范围”里填写的 App 内自动检测广告**（默认 `com.phoenix.read`），
> 避免在聊天、设置、桌面等普通界面把页面上的“广告/关闭/跳过”等文字误判成广告而自动点击。
> 若需在其它短剧 App 使用，把它的包名追加到该列表（逗号分隔）并保存；
> 若确实想在**所有 App** 内都尝试通用关键字匹配，可**关闭**“仅检测下方 App（推荐）”开关（误触风险更高）。
> 开关下方会实时显示当前生效范围：`✅ 当前生效：只检测下方列表内的 App` /
> `⚠️ 当前生效：检测「所有 App」的广告` / `已修改，点「保存规则」后生效`。
>
> 其它短剧 App 即使加入列表，也仅通过通用的关键字匹配（"上滑继续观看 / 跳过广告 / 关闭 / 倒计时"等）生效，
> 但**不保证可靠**：若广告文字由视频层（SurfaceView）绘制将无法识别；正剧播放保护词表不匹配
> 也可能误滑。若需支持其它 App，可追加关键词，或把**广告截图 + App 名称**
> 提交到项目 Issues / Telegram 群组，我们会针对性补充规则。
>
> 💬 **反馈与交流**：加入 Telegram 群组 [AdAuto 用户交流群](https://t.me/+I5jUPxmH_jA0OWNh) 反馈问题、提建议，或直接发广告截图，我们会尽快补充规则。

## 功能特性

| 特性 | 说明 |
| --- | --- |
| 悬浮控制球 | 屏幕左上角显示球形助手，可拖动；点击快捷开关"自动跳过"，长按打开设置页 |
| 无障碍自动跳过 | 监听界面变化，检测到广告后自动点击"跳过/关闭"或执行上滑手势 |
| 短剧上滑识别 | 识别"上滑继续观看短剧 / 上滑继续"等关键字并自动上滑 |
| 自定义关键词 | 可在设置页追加"跳过按钮"关键词，支持中英文逗号/顿号分隔 |
| 自动跳过范围 | 默认仅在“规则设置→自动跳过范围”填写的 App 包名内检测广告；**开关打开 = 仅检测下方 App（推荐），关闭 = 对所有 App 生效**；开关下方实时显示当前生效范围 |
| 倒计时广告识别 | 识别"X秒后可继续 / 倒计时 / 后继续观看 / **后可继续上滑（滑动锁）**"等文案，倒计时结束后自动点击"继续观看"或上滑划走 |
| 防误触 | 点击类规则默认要求出现"广告/倒计时"上下文，降低误触风险；内置节流防重复触发 |

## 支持的广告类型（内置规则）

1. **上滑继续观看短剧**：页面出现"上滑继续观看/上滑继续/继续观看短剧" → 自动执行**上滑**手势
2. **跳过广告**：出现"跳过 / 跳过广告 / 跳过此广告 / skip" → 自动**点击**
3. **关闭广告**：出现"关闭 / 关闭广告 / ×"，且页面有广告上下文 → 自动**点击**
4. **知道了/确定**：广告弹窗提示 → 自动**点击**
5. **倒计时广告**：出现"X秒后可继续 / 倒计时 / 后继续观看"等 → 判定为广告页；倒计时结束出现"继续观看/继续播放"按钮 → 自动**点击**
6. **红果图文/商城卡片广告**：出现商城卡片 banner"好物省心选"且页面文字极少 → 自动**上滑**（见下方红果专用增强）
7. **红果广告 feed item**：出现广告 item 容器（`ay0`+`i0t`，创意整张画在位图里时只有几个文字碎片）→ 自动**上滑**

> 广告上下文判定：页面出现"广告"字样，或出现倒计时（如 "5秒"、"3s"、"X秒后可继续"）。
>
> ⚠️ **不再主动“点屏幕正中”（2026-10-23）**：早期为了跳过“需倒计时等待”的广告，会在检测到倒计时后
> **点一下屏幕正中**让视频暂停，从而提前解锁上滑。实测反馈：**某些直播类/落地页类广告会把“点中心”
> 当成点击广告创意，过几秒就自动进入直播间/落地页**。现已**彻底移除**该动作（代码里已无 `tapCenter`）：
> - 广告**已经**处于暂停态时（中央出现播放按钮，**只读**判定）→ 等底部“上滑”提示出现后划走；
> - 否则回退为“等倒计时结束再滑动”——仍能跳过，只多等几秒，但零误点风险。
>
> 因此现在**主动操作只有两类**：① **上滑手势**（`dispatchGesture`，唯一的手势动作）；
> ② **文字触发的点击**（`跳过广告 / 跳过 / 关闭 / 知道了 / 继续观看 / 自定义关键词`，
> 且除“跳过广告/跳过此广告”外都要求页面存在广告上下文）。
>
> ⚠️ **倒计时广告：优先点“跳过/关闭”，不再傻等倒计时（2026-10-23）**：Pangle 广告常同时挂着
> “跳过 5s”按钮和“上滑继续观看”提示。旧顺序里上滑判定在前，而倒计时期间滑动被锁住 → 只能干等
> 到倒计时归零（用户反馈“不该等这 5 秒”）。现在在 `match()` 开头（正剧保护之外）先尝试点
> “跳过/关闭”按钮，**点得到就立即跳**；点不到再回退到上滑/等倒计时。另外 `perform()` 新增护栏：
> **目标若覆盖 ≥ 60% 屏幕则拒绝点击**（那几乎都是广告创意/整页容器，点它等于点进落地页/直播间）。
>
> ℹ️ **红果专用增强**：红果的广告由穿山甲（Pangle）SDK 以视频层（SurfaceView）渲染，提示文字不在
> 无障碍树内、关键字匹配不到。已做专门处理：**广告期间无正剧播放控件 + 出现可点击的"立即领取"
> 即判定为广告并自动上滑**；正剧播放期间会出现"倍速/选集/热评/分享/暂停/第X集"等控件，此时**绝不**
> 滑动/点击（正剧保护）。该增强仅对红果 App 生效，其它 App 无此逻辑。
>
> ℹ️ **红果「直播样式」广告（2026-09 新增）**：红果新版广告采用抖音直播样式创意（"直播中 / 主播名 /
> 商品讲解 / 领取 / 点击进入直播间 / 上滑继续看短剧"），**整屏由视频层绘制，无障碍树里一个文字节点都
> 没有** —— 上滑关键字、立即领取、广告角标、倒计时、点击规则全部失效，表现就是"广告跳不过"。
> 识别方式：这类广告会挂上一个**具名渲染视图** `com.phoenix.read:id/ttlive_player_render_view`
> （正剧播放始终走 `SurfaceView`、任何状态下都不会出现它，实测 5 份正剧样本 vs 19 份直播广告样本），
> 检测到即判定为广告并**直接上滑**（不走"点中心暂停"流程，避免误入直播间）。
> 为能看到广告浮层，无障碍服务额外声明了 `flagReportViewIds` 与 `flagIncludeNotImportantViews`
> —— 广告 SDK 会把广告浮层标记成"对无障碍不重要"，缺后一个 flag 时节点树里根本看不到它们。
>
> ℹ️ **红果「滑动锁」与两段式补扫（2026-10 新增）**：横屏全屏广告有 **`5s后可继续上滑观看`**
> 这类**滑动锁**（锁期内滑动一律无效，横屏实测锁期约 **12 秒**）。关键事实：这句提醒**画在视频层里、
> 无障碍树读不到**（实测 `countdown=false`、textLen 只有广告主文案），因此**只能靠“广告还在屏上但
> 划不走”这个信号来驱动补扫**。旧实现快速补扫 7 次（≈5s）就把预算烧光，随后掉进穿山甲 6000ms 冷却
> —— 白等到 12s 才划走。现在改为**两段式节奏**：
> - **入场期**：每 `700ms` 补扫一次，共 7 次（≈4.2s），覆盖“上滑落在入场动画上没生效”；
> - **看门狗期**：改为每 `1500ms` 补扫一次，一直重试到总预算 `40s` 或硬上限 30 次 ——
>   锁一解除就能在 **1.5s 内**划走，不再白等 6s 冷却；
> - 倒计时/暂停推迟期间**结束上滑链**（锁期不算“划了没生效”），避免预算被锁期烧光；
> - 冷却中不再静默返回，而是**排定“冷却结束即补扫”**（日志按 500ms 节流），静止广告也能准时跳过。
>
> ℹ️ **红果「图文 / 商城卡片」广告（2026-10 新增）**：另一种跳不过的形态（实测样本：肯德基疯狂
> 星期四「图集 0/4」+ 商品卡“红果优选 / ¥18.8 / 不感兴趣 / 去商城购买”）。广告卡住时整棵无障碍树
> **只有两个文字节点**：`desc="商城好物省心选"`（商城卡片固定 banner）与 `text="领取"`；
> 底部的“上滑继续看短剧”提示**画在视频层上、读不到**（与“家博会广告”那条原生 `rid=apt` 的提示不同），
> 且无“广告”角标 / 无倒计时 / 无渲染视图 → 旧规则全部漏掉。
> 现已按 banner 判定为广告并**直接上滑**（实测上滑能划走，**不点“领取”**——那是领券/落地页）：
> - 条件：页面文字含 `好物省心选` **且** 文字节点数 ≤ 6（正剧/内容页/商城页文字远多于此）；
> - ⚠️ **不用“右边缘的『领取』CTA”作判据**：实测**正剧状态下也有一个完全相同的节点**
>   （`text="领取"`、bounds `[1137,901][1179,989]`、祖先 `ViewGroup [CLICKABLE] [1068,819][1200,1071]`），
>   说明它是常驻元素（红果自己的福利入口 / SDK 常驻 widget），单用它在正剧上会误判。
>
> ℹ️ **红果「试玩 / 游戏落地」广告（2026-10 新增）**：又一种跳不过的形态（实测样本：“台球王者”
> 试玩广告 —— 画面上有游戏 UI、`点击进入游戏`、`4亿人都在玩的3D真人台球游戏`，底部"上滑继续看短剧"）。
> 它的创意（含所有按钮和文字）**全画在一块没有 `resource-id` 的 `TextureView` 上**，
> 所以无障碍树里 `textLen=0`、只有 1 个可点击节点（左上返回），也没有“广告”角标/倒计时/具名 id。
> 关键对照（同日实测）：**正剧始终走 `android.view.SurfaceView`（`[0,0][1200,2360]`），全程不会出现
> TextureView**；正剧播放时 `nodes=89 textLen=108`，而这条广告是 `nodes=20 textLen=0`。
> 因此把广告渲染视图的判据从“具名 id `ttlive_player_render_view`”**泛化为“类名 TextureView”**：
> **仅在竖屏**检测到 TextureView 即判定为广告渲染视图 → 直接上滑（实测上滑能划走）。
> 位置仍在正剧保护之后，且该分支自带 `immediate=true`（不走倒计时/点中心暂停流程）。
> ⚠️ **必须限定竖屏（2026-10-27 修正）**：横屏全屏时红果正剧的视频层**有时本身就是 TextureView**
> （同一台设备先后采到 `surface=YES texture=no` 与 `surface=no texture=YES` 两种正剧状态），
> 若不限方向会造成**横屏正剧被当成广告连续划走**。
>
> ℹ️ **红果「电商卡片（位图创意）」广告 + 广告容器判据（2026-10 新增）**：实测样本是 iQOO Pad5 Pro
> 平板广告（图集 1/5，`叮～送你7折优惠券`、`券后价￥689`、`去商城领券`）。它的创意**整张画在位图里**，
> 无障碍树只剩优惠券动画的几个文字碎片（`叮～送你` / `7` / `折优惠券` / `7折`，`textLen=15`），
> 既没有 TextureView / 具名渲染视图 / 角标 / 倒计时 / banner → 旧规则全部漏掉。
> **解决办法**：实测**三种广告形态**（图文商城卡片 / 台球试玩 / 本条电商卡片）的无障碍树里
> **都同时含有** `com.phoenix.read:id/ay0` 与 `id/i0t` 这两个广告 item 容器，而正剧 dump
> （84 个 id）里两个都没有（正剧时它们是 GONE）→ 据此新增判据“两个 id 同时存在即判定为广告”。
> 已验证：本条广告上滑可划走（`nodes=24 textLen=15` → `nodes=88 textLen=124`）。
> ⚠️ 这两个是混淆后的短名，红果升级可能改名；失效时只会“漏跳”（安全方向），重新取证补判据即可。
>
> ℹ️ **名称无关兜底：稀疏树广告（2026-10 新增）**：针对“创意整张画在位图/表面里、无障碍树几乎
> 没内容”的广告，加了一条**不依赖任何具体 id 名或创意文案**的兜底判据（用户实测提出）。
> 条件（全部满足）→ 直接上滑：
> - **仅竖屏**：横屏正剧实测 `textLen=0`，与广告特征完全撞车，所以横屏不做此判定；
> - 文字总量 ≤ 30 字符（正剧 96~133；广告实测 0~15）；
> - **页面存在视频表面**（SurfaceView/TextureView）——广告创意画在视频层上，纯图片列表页没有；
> - **页面没有可滚动容器**（列表 / 网格 / ViewPager）——全屏广告创意不会带滚动结构，内容页一定带；
> - 无正剧播放控件；
> - **持久性确认 800ms**：该判据是“缺失型”，广告→正剧的过渡帧也会命中，因此要求同一状态连续
>   满足 ≥800ms 才动手，动作后再清零重新确认。
>
> ⚠️ **2026-10-31 修正（红果“新剧推荐”误划）**：**弃用了“节点数 ≤ 40”这条数字阈值**。
> 该阈值是用 **uiautomator 原始节点数**标定的（“正剧 84~92 / 广告 20~26”），但代码里比较的却是
> `AdDetector.collectNodes` **过滤后**的节点数（只保留带文字/描述/资源 id/TextureView 的节点），
> 口径不一致：红果「新剧推荐」列表页（纯自绘海报，原始 84~98 节点、0 文字）被压成 4~6 个节点，
> 直接落进广告区间 → **一开助手就把正常浏览页上滑**（logcat 实测 `nodes=4 textLen=0 sparse=true`）。
> 而实测真实广告的原始节点数是 64~74，同样超过 40 —— 继续用数字阈值反而会**漏跳真广告**。
> 现在改用结构判据（有视频层 + 无可滚动容器 + 读不到文字），才能真正区分“全屏创意”与“内容列表页”。
>
> ⚠️ **同一次修正（TextureView 规则）**：`广告(渲染视图TextureView)` 原来只要求“竖屏 + 出现
> TextureView”，而 `collectFromAllWindows` 会把**同包名、非活动**的旧窗口节点一并收进来 ——
> 从短剧播放页退出到「新剧推荐」时，正在淡出的播放器窗口带着 `TextureView` + 61 字文本泄漏进来，
> 静置时莫名上滑两次。现在该规则同样要求 **文字总量 ≤ 30 且无可滚动容器**。
>
> 好处：以后出现“完全认不出”的稀疏型广告也能自动跳过，不必再逐个补判据。
>
> ⚠️ **以上红果专属判据只在 `com.phoenix.read` 上生效（2026-10-23 修复）**：渲染视图 / 广告角标 /
> 商城卡片 banner / 广告 item 容器（`ay0`+`i0t`）/ 稀疏树，这几条都是按红果广告形态逐个取证出来的
> 启发式，而“稀疏树”本质是**缺失型**判据（靠“节点少 + 文字少”反推）。已有人反馈：某读书 App 的
> 正文用 Canvas/SurfaceView 绘制，无障碍树同样“稀疏”，在开启了通用模式的机器上被兜住后**一直
> 自动划页**。因此给这些判据统一加了**包名闸门**：只有前台包名 == `com.phoenix.read` 才参与判定。
> 通用规则（上滑关键字 / 跳过·关闭点击 / 倒计时 / 自定义关键词）不受影响，仍可在“通用模式”
> 或自定义支持包名里工作。
>
> ℹ️ **横屏（全屏）视觉兜底：橙色按钮（2026-10-27 新增）**：横屏全屏播放时，红果会把正剧控件
> **全部隐藏**，无障碍树里既没有正剧特征也没有广告特征 —— 实测横屏广告的树是 **50 节点 / 0 文字**，
> 连画面上的“上滑继续看剧集”“查看详情”“广告”都读不到，所以纯节点规则在这里无解。
> 解决办法（用户思路）：**截图 + 颜色统计**（不做 OCR）判断“画面里有没有一个实心橙色宽按钮”。
>
> - 触发条件：`action == null` + **横屏** + 前台是红果 + 无正剧播放控件 + 不在动作冷却期；
> - 判据**不是**橙色像素占比 —— 实测横屏正剧占比 9.8% 反而**高于**广告的 7.2%；
>   真正的区分点是**最大橙色连通块的形状**（实心 / 够宽 / 够矮 / 宽高比大 / 位于中下部）：
>
>   | 画面 | 橙色占比 | 最大连通块 | 填充率 | 长宽比 | 判定 |
>   |---|---|---|---|---|---|
>   | 横屏广告（“查看详情”按钮） | 7.2% | 2080×108 | **0.97** | 19.3 | 命中 |
>   | 横屏正剧 | 9.8% | 336×360 | 0.41 | 0.9 | 拒绝 |
>   | 竖屏正剧 | 3.0% | 160×176 | 0.43 | 0.9 | 拒绝 |
>   | 广告里的细“上滑提示”条 | 0.9% | 712×72 | 0.19 | 9.9 | 拒绝（填充率不够） |
>
> - 门限（形态 A：横贯屏幕的宽条）：填充率 ≥0.65、宽 ≥25% 屏宽、高 20px ~ 30% 屏高、
>   长宽比 ≥2.5、中心 Y ≥30% 屏高；
>
> ℹ️ **另一种形态：右下角的小橙色按钮（2026-10-27 追加）**：直播/电商类横屏广告的 CTA
> 是**右下角一个小方块按钮**（“查看详情”），实测 `216×84`（屏 2670×1200，宽只有 8.1% 屏宽），
> **宽不到形态 A 的 25% 门槛**，而且**它不是画面里最大的橙色块** ——
> 最大的那块是 224×132、填充率 0.56 的零碎橙色，旧代码“只看最大连通块”直接被它盖掉。
> 所以改成**逐连通块判定**（不再只看最大块）并新增形态 B：
>
> | 形态 | 填充率 | 宽度 | 高度 | 位置 |
> |---|---|---|---|---|
> | A 横贯宽条 | ≥0.65 | ≥25% 屏宽 | 20px ~ 30% 屏高 | 中心 Y ≥0.30 |
> | B 右下角小按钮 | **≥0.75** | 5% ~ 20% 屏宽 | 3% ~ 15% 屏高 | 中心 X ≥0.75 且 中心 Y ≥0.80 |
>
> 实测分离度：广告样本 `216×84` 填充 **0.82** 中心 (0.85, 0.92) → 命中；
> 横屏正剧样本同区域最大块 `200×124` 填充 0.61 中心 X 0.42 → 拒绝。
>
> ℹ️ **再加两层判据：颜色纯度 + 近似矩形（2026-10-27，用户提出）**
>
> - **颜色纯度**：视频画面里的"橙色"是几百种色值混在一起，而 UI 按钮是同一个色值。
>   做法：网格里存**采样到的颜色**（不再是布尔掩码），逐块算出块内 RGB 均值，统计
>   落在 **±12** 带内的像素占比。实测：
>
>   | 区域 | 均值 | 最大标准差 | ±12 带内占比 |
>   |---|---|---|---|
>   | 广告右下角 CTA | `#EF8E3E` | **6.9** | **0.98** |
>   | 广告里的视频橙块 | `#BD8953` | 17.8 | 0.38 |
>   | 正剧里的橙块（最大） | `#A1744F` | 12.8 | 0.54（同机另一样本最高 0.76） |
>   | 正剧画面（真机 20 次探测） | `#AB7152` 等 | — | 0.38 ~ 0.52 |
>
>   门槛 **纯度 ≥0.85**，分离度远大于"形状/填充率"。
>
> - **近似矩形**：只看填充率不够 —— 斜向色带、L 形、圆弧也能填满外接框一半。
>   矩形的特征是"**每一行的横向跨度都接近外接框宽度，每一列的纵向跨度都接近外接框高度**"。
>   逐块统计：单行/单列跨度需 ≥ 外接框该方向尺寸的 80%，且满足该条件的行、列占比都要 ≥ 0.70。
>
>   | 区域 | 行跨比例 | 列跨比例 |
>   |---|---|---|
>   | 广告 CTA | **1.00** | **0.94** |
>   | 广告里的视频橙块 | 0.00 ~ 0.59 | 0.26 ~ 0.70 |
>   | 正剧橙块 | 0.09 ~ 0.92 | 0.26 ~ 0.92（但纯度仅 0.23） |
>
>   三层判据（形状 A/B + 纯度 + 矩形）**全部满足**才判为广告按钮。实现上复用同一趟
>   连通块遍历，行/列跨度用 stamp 数组避免每块重置，成本仍是一次遍历（后台线程采样）。
>
> ℹ️ **静止广告的“续命轮询” + 低频看门狗**：横屏广告的视频层画在 surface 上、叠加文字不再刷新时，
> 无障碍**一个事件都没有** —— 实测现场上滑补扫链结束后 logcat 静默 **10 分钟以上**，
> 广告一直挂着不划。两层兜底：
> 1. **横屏兜底轮询**：只要处于横屏模糊态且没拿到动作，就自己定期重扫（1.5s 间隔；
>    加时间闸门 —— 内容变化事件每秒十几次，不加闸门 4 秒就把预算烧光；
>    最多 40 次 ≈ 60s，换窗口/动作后重置预算；冷却期内把重扫排到冷却结束）；
> 2. **低频看门狗**（`AdDetector.startWatchdog()`，服务连接时启动）：**不依赖任何无障碍事件**，
>    每 3s 检查一次，距上次检测超过 2.5s 就自己扫一遍。没有它的话界面完全静止时
>    `detectAndAct` 根本不会被调用，上面的轮询也就永远启不动（实测重装后 20s 内日志 0 行）。
>    成本很低：不在支持范围内的 App 在包名闸门处直接返回，不会遍历节点树。
>
> - **必须两张不同截图都命中**才动作（同一张图不重复计数），避免视频画面偶发偏橙误判；
>
> ℹ️ **截图什么时候才会发生（闸门链，2026-10-27 实测核对）**
>
> 截图**不是**一直生效的，要依次通过这些闸门（任何一条不满足就完全不截）：
>
> | # | 闸门 | 不满足时的行为 |
> |---|---|---|
> | 1 | `自动跳过` 开关打开 | 事件与看门狗都直接返回（日志`自动跳过已关闭`） |
> | 2 | 前台不是自己/系统 UI（`NON_AD_PACKAGES`） | 返回，不遍历节点树 |
> | 3 | 前台在「支持的包名」里（默认只有 `com.phoenix.read`） | 返回（实测在系统设置里 `scan=0`） |
> | 4 | 不在拖动悬浮球期间 | 返回 |
> | 5 | `AdRules` 节点判据**没有**给出动作 | 有动作就直接执行，不截图（节点判据更快） |
> | 6 | **横屏**：`frameW > frameH` | 竖屏完全不截（实测竖屏红果 12s 内截图 0 次，但 `scan` 仍在跑） |
> | 7 | **前台包名 == `com.phoenix.read`**（`isLandscapeAmbiguous` 内单独再判一次） | 其它 App 即使横屏也不截 |
> | 8 | 读不到正剧控件（`!hasPlaybackControls`） | 能读到「倍速/选集/第 X 集」就不截 |
> | 9 | 不在动作冷却期 | 冷却期内不截，把重扫排到冷却结束 |
> | 10 | `requestOrangeProbe` 自身：API≥30、不在飞行中、距上次 ≥1.2s | 直接 return |
>
> 频率（1.0.17 起）：
> - 预算内（前 40 次轮询）：结果有效期 2.5s、自我轮询 1.5s、硬下限 1.2s；
> - **预算用完后降频到 8s 一张**（日志 `轮询 40 次用尽，降频为 8000 ms/次`），
>   既省电又不会在"看了很久正剧之后突然出广告"时完全漏掉；
> - 实测横屏红果 15s 内 5 张（≈1/3s）；竖屏红果 12s 内 0 张；系统设置里 0 张 0 扫描。
> - 实现：`AccessibilityService.takeScreenshot()`（需 `android:canTakeScreenshot="true"`，API 30+），
>   截图在**后台线程**做 step×step 盒平均 + 4 邻域连通块统计，主线程不参与像素运算；
>   探测间隔 ≥1.2s，结果有效期 2.5s，命中一次后再取一张新图确认。
> - ⚠️ 只在“模糊态”生效：一旦能读到正剧控件或任何广告特征，就走原有（更快更准的）节点判据。
>
> ℹ️ **重要坑：无障碍截图是 Display P3，不是 sRGB**（2026-10-27 实测）
>
> 日志打过缓冲元数据：`hw=2670x1200 fmt=1 layers=1 cs=Display P3`。
> - `fmt=1` = `RGBA_8888` → **没有任何压缩/编解码**，所以"截图被压缩成散色"的说法不成立；
> - 真正的原因是**色彩空间**：无障碍截图给的是广色域 P3 的原始像素，而 `adb screencap`
>   和人眼看到的是 sRGB。同一根橙色按钮：P3 下均值 `#FE8720`、中线采样 `#FF7E0C #FF7F0F…`（带渐变），
>   sRGB 下均值 `#EF8E3E`、±12 纯度 0.998。**两份数值本来就不该相等**。
> - 后果：不转色域直接算"颜色纯度"，真按钮只有 0.68，而正剧块反而能到 0.94 → 判据失效。
> - 修复：分析前先 `Canvas` 画到一张 **sRGB** 位图（`Bitmap.createBitmap(..., ColorSpace.get(SRGB))`），
>   既统一了色彩空间，也顺带把 HARDWARE 位图转成可 `getPixels` 的软件位图。
> - **几何量（填充率 / 行跨 / 列跨）在两条路径下完全一致**（同一根按钮两边都是 0.97 / 1.00 / 0.98），
>   所以判定以几何为主，颜色纯度只作排查日志。

## 工作原理

```
其他应用界面变化
      │  AccessibilityEvent (TYPE_WINDOW_STATE_CHANGED / CONTENT_CHANGED)
      ▼
AdSkipAccessibilityService（无障碍服务）
      ▼
AdDetector：遍历当前窗口节点树（BFS，仅保留可见节点）
      ▼
AdRules：关键字匹配
      ├─ 命中"上滑继续观看短剧"  → dispatchGesture 上滑
      ├─ 命中"跳过/关闭/知道了"  → 找到可点击节点 → performAction(ACTION_CLICK)
      └─ 命中用户自定义关键词     → 同上
```

悬浮球由 `FloatingBallService`（前台服务 + `WindowManager`）承载，与无障碍服务通过 `SettingsManager`（SharedPreferences）共享开关状态。

## 使用步骤

1. **安装并打开应用**，进入设置页。
2. 依次完成三项授权（页面内点"去开启/去授权"即可跳转）：
   - **无障碍服务**（必开）：系统设置 → 无障碍 → 已安装的服务 → 广告快跳无障碍服务
   - **悬浮窗权限**（必开）：允许显示在其他应用上层
   - **通知权限**（Android 13+）：用于前台服务常驻通知
3. 确认"自动跳过广告"与"显示悬浮球"两个开关为开启状态。
4. 返回桌面，屏幕**左上角**即出现悬浮球，开始自动工作。

| --- | --- |

| 点击 | 快捷开关"自动跳过广告"（球体变灰 = 已关闭） |

- 设置页底部的 **"立即检测当前界面"**：手动触发一次检测，返回当前界面是否处于广告状态，方便验证规则。
- 规则设置里的自定义关键词可追加"跳过按钮"文字（默认已内置常见词）。

## 说明与限制

- 本应用**仅用于跳过应用内广告**，不会收集、上传任何个人数据；所有处理均在本地完成。
- **关闭「显示悬浮球」时球体会变成完全透明（窗口与后台服务都保留，左上角那片区域也不挡触摸）**：这是为了保证自动跳过继续生效。实测小米 / HyperOS 下，如果应用没有前台服务，被切到后台约 20 秒后就会被系统挂起（进程仍在、无障碍也显示已授权，但再也收不到界面变化事件，广告就不会被跳过）。想彻底退出，请把「自动跳过」和「显示悬浮球」**都关闭**。
- **默认仅在“规则设置 → 自动跳过范围”指定的 App 内检测**（默认 `com.phoenix.read`），避免在普通界面
  把页面上的“广告/关闭/跳过”等字样误判成广告自动点击；可把其它短剧 App 的包名追加到列表，
  或开启“通用模式”对所有 App 生效（误触风险更高）。
- **当前为「红果免费短剧」App 专用适配**：正剧播放保护、穿山甲广告识别（立即领取→上滑）、窗口切换延迟重扫均按红果的界面/广告形态调优。其它 App 仅有通用关键字匹配兜底，可靠性不保证。
- 检测会自动屏蔽本应用自身（设置页含"自动跳过/广告快跳"等文字），且在非活动窗口/系统设置窗口不会触发任何动作，避免误触。
- 无障碍服务仅在检测到广告关键字时才执行点击/手势，且带 1.5s 节流防重复触发。
- 某些广告（如全屏原生广告、无"跳过"文字的贴片广告）可能无法识别，可在"规则设置"中追加关键词增强识别。
- Android 12+ 限制后台启动前台服务：无障碍服务连接时若应用处于后台，可能无法自动拉起悬浮球，此时请在设置页手动打开"显示悬浮球"开关（或在应用内点击开启）。

## 常见问题与排障（FAQ）

### Q1：提示"未知来源应用，系统已拒绝此应用获取敏感权限"，无法开启无障碍

**原因**：安装的是 **debug 签名**的 APK（`./gradlew assembleDebug` 打的包）。MIUI / HyperOS 出于安全策略，会拒绝 debug 签名应用获取无障碍、悬浮窗等敏感权限。

**处理**：
1. 改装 **release 签名包**：`./gradlew assembleRelease`，产物为 `app/build/outputs/apk/release/app-release.apk`
2. 若设备上已装有旧包（debug 或不同签名），需**先卸载**再安装（签名不一致无法覆盖安装）：
   ```bash
   adb uninstall com.wisight.adauto
   adb install app/build/outputs/apk/release/app-release.apk
   ```
3. 卸载重装会清空应用数据，安装后需重新开启三项权限并恢复设置。

### Q2：无障碍开关明明开着，过一阵自动失效了（小米 / HyperOS 常见）

**原因**：MIUI / HyperOS 在以下场景会**静默清除无障碍设置**：
- 在设置/应用管理里**强行停止**了本应用
- 手机管家的**垃圾清理 / 电池优化**杀了后台
- **重启手机**（部分版本）
- 应用长期未使用被系统回收

**症状**：悬浮球可能还在，但不再自动跳过广告（因为无障碍服务已断开）。

**处理**：
1. 打开 **设置 → 无障碍 → 已下载的服务 → 广告快跳无障碍服务**，重新打开开关
2. 或使用 adb 一键恢复（设备已开启 USB 调试）：
   ```bash
   adb shell settings put secure enabled_accessibility_services com.wisight.adauto/.service.AdSkipAccessibilityService
   adb shell settings put secure accessibility_enabled 1
   ```
3. 确认是否生效：
   ```bash
   adb shell dumpsys accessibility | grep "Enabled services"
   ```
   输出应包含 `com.wisight.adauto/.service.AdSkipAccessibilityService`

**预防**（减少被撤销的概率）：
- 在**最近任务**里下拉**锁定**广告快跳
- 手机管家 → 应用管理 → 权限 → 打开**自启动**，省电策略设为**无限制**

### Q3：覆盖安装（升级）后悬浮球不见了

**原因**：覆盖安装瞬间系统可能短暂判定"显示在其他应用上层"权限未就绪，导致悬浮球未自动拉起（应用会弹出系统授权页，属正常现象）。

**处理**：重新打开一次应用主界面即可自动拉起悬浮球；若仍未出现，到 **设置 → 应用 → 广告快跳 → 显示在其他应用上层** 确认权限为"允许"。

### Q4：升级时报"安装失败 / 签名不一致"（INSTALL_FAILED_UPDATE_INCOMPATIBLE）

**原因**：新包与已安装包**签名不同**。常见于：debug 包与 release 包混装、或更换了 keystore 重新签名。

**处理**：
- 始终用**同一把 keystore** 签名（见下节"发布与签名"）
- 若签名确实已变，只能**卸载后重装**（会清空设置，需重新授权）

### Q5：某些广告跳不过去（无"跳过"文字、纯图片按钮）

**原因**：无障碍服务只能读取到带 `text` / `contentDescription` 的节点；**纯图片按钮读不到文字**，因此无法自动点击。

**处理**：
- 在设置页"规则设置"中追加该广告上的可见关键词
- 或在项目里为特定 App 增加针对性的规则（欢迎反馈截图）
- 遇到跳不过的广告，也可将截图发到 [Telegram 群组](https://t.me/+I5jUPxmH_jA0OWNh)，我们会针对性补充规则

## 发布与签名

- 签名文件：`keystore/adauto.keystore`（RSA 2048）
- 签名配置：`keystore.properties`（内含 keystore 密码与 keyAlias）
- 两者均已加入 `.gitignore`，**不会**提交到仓库

> ⚠️ **请务必备份 `keystore/adauto.keystore` 和 `keystore.properties`！**
> Android 升级安装要求新旧包**签名一致**。一旦丢失 keystore 或密码：
> - 无法对旧用户做无缝升级（只能卸载重装，丢失所有设置）
> - 只能重新生成 keystore，此时视为"全新应用"
>
> 建议：将这两个文件复制到安全的离线位置（网盘/加密盘）妥善保管。
